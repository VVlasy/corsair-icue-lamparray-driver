# Phase 0 research summary

The project brief required that no implementation begin until the relevant
specifications and samples had been read and summarised, and in particular
that the HID descriptor **not** be written from memory. This document records
what was found and what was decided as a result.

The short version: the descriptor is reproduced byte for byte from Microsoft's
own LampArray firmware sample, and every behavioural rule the driver implements
is cited back to a numbered section of the USB HID Usage Tables.

## What the specification actually requires

Usage page **0x59** ("Lighting And Illumination"), top-level usage **0x01**
(`LampArray`), containing six reports. The single most consequential fact:

> **Every LampArray report is a Feature report.** There are no Input and no
> Output main items anywhere in the descriptor.

That determines the driver's entire shape. The whole protocol arrives as
`IOCTL_HID_GET_FEATURE` and `IOCTL_HID_SET_FEATURE`, so the driver registers
exactly two VHF callbacks and needs no read-report path, no
`VhfReadReportSubmit`, and no input buffering policy. `tests/HidTests`
asserts this against the descriptor rather than trusting the observation.

| Report | Id | Direction | Payload | Purpose |
|--------|----|-----------|---------|---------|
| `LampArrayAttributesReport` | 1 | GET | 22 B | Lamp count, bounding box, kind, min update interval |
| `LampAttributesRequestReport` | 2 | SET | 2 B | Select which lamp to interrogate |
| `LampAttributesResponseReport` | 3 | GET | 28 B | That lamp's position, purposes, colour levels |
| `LampMultiUpdateReport` | 4 | SET | 50 B | Up to 8 lamps, each a different colour |
| `LampRangeUpdateReport` | 5 | SET | 9 B | One colour across a contiguous LampId range |
| `LampArrayControlReport` | 6 | SET | 1 B | Autonomous mode on/off |

Behavioural rules that are easy to get wrong, and are therefore each covered by
a named test:

- **§26.8.2 — the attribute cursor auto-increments and wraps.** After
  responding for `LampCount-1` the device resets to 0. (Microsoft's RP2040
  sample clamps instead of wrapping; the specification says wrap, and this
  project follows the specification.)
- **§26.8.1 — an invalid `LampId` is treated as `LampId == 0`,** not as an
  error.
- **§26.11.1 / §26.11.2 — an update report containing *any* error must be
  ignored in its entirety.** Not partially applied. Errors include a `LampId`
  at or beyond `LampCount`, a duplicate `LampId` in two slots, a channel value
  above that lamp's declared level count, and `LampIdStart > LampIdEnd`.
- **§26.11 — `LampUpdateComplete` ends a batch.** Preceding updates are
  accumulated and applied as one frame.
- **§26.10.1 — autonomous mode defaults to enabled,** and the attribute
  reports must keep working regardless of its state.
- **§26.9 — a level count of N means values 0..N are legal.**

That last rule has a practical consequence worth stating plainly, because
getting it wrong produces a device that looks correct and silently does
nothing: if a lamp declared `IntensityLevelCount = 1` and Windows sent
intensity 255, §26.11.1 would require the device to discard the whole report.
This project therefore declares **255 on every channel of every lamp**, so no
colour Windows can express is ever out of range. See `docs/lamp-array.md`.

## Questions the documentation did not answer directly

**Does the transfer buffer include the report ID?** The `HID_XFER_PACKET`
documentation says only "pointer to a report buffer" and describes `reportId`
as optional. The answer came from Microsoft's own KMDF minidriver sample,
`hid/vhidmini2/driver/vhidmini.c`, which computes
`sizeof(payload) + sizeof(packet.reportId)` and reads the payload from
`reportBuffer + sizeof(reportId)`, with the comment:

> "Since this device has one report ID, hidclass would pass on the report ID in
> the buffer (it wouldn't if report descriptor did not have any report ID)."

So the buffer is `[reportId][payload]` and `reportBufferLen` counts the ID
byte. The driver checks the ID from the buffer against `packet->reportId` and
refuses the operation if they disagree, rather than guessing which to trust.

**At what IRQL do the VHF callbacks run?** `EVT_VHF_ASYNC_OPERATION` is
documented as **IRQL <= DISPATCH_LEVEL**. This is why per-device state is
guarded by a `WDFSPINLOCK` rather than a wait lock, why every buffer the
callbacks touch is `NonPagedPoolNx`, and why nothing that can block happens
inside the lock.

## Was this already built?

The brief asked for the upstream state to be re-checked. Nothing was found
that bridges the iCUE SDK to a VHF virtual HID LampArray. The adjacent work is:

- **OpenRGB** — talks to Corsair hardware directly over USB, bypassing iCUE
  entirely. Solves a different problem and requires the vendor protocol
  reverse engineering this project explicitly avoids.
- **Microsoft's firmware samples** — LampArray on real firmware, no Windows
  driver and no vendor SDK.
- **Corsair's own iCUE** — controls the hardware but does not expose it to
  Windows Dynamic Lighting.

Microsoft documents VHF as a supported route to a Dynamic Lighting device, and
the iCUE SDK provides device enumeration, LED positions and colour setting.
The architecture is therefore sound and the gap is real.

## Consequences for the design

1. **Feature reports only** — two VHF callbacks are the whole host-facing
   surface.
2. **One static descriptor serves every device.** It encodes no lamp count:
   `LampCount` is runtime data in report 1 and every `LampId` field is 16 bits.
3. **Lamp attributes are static** (§26.8.3), so the service can push the whole
   lamp table to the driver once at creation and the driver can answer
   interrogation with no user-mode round trip. This is what keeps the HID path
   fast and keeps enumeration working while the service restarts.
4. **A spinlock, not a wait lock**, and non-paged memory throughout the report
   path.
5. **Positions in micrometres, times in microseconds** (§26.6), as signed
   32-bit quantities.
6. **Assign LampIds methodically, top-left first** (§26.8.1), because
   contiguous runs let the host collapse updates into range updates instead of
   one multi-update per eight lamps.
