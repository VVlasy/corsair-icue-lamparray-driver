# The HID report descriptor

## Provenance

`core/src/LampArrayDescriptor.cpp` contains 292 bytes reproduced **verbatim**
from Microsoft's LampArray firmware sample:

> <https://github.com/microsoft/ArduinoHidForWindows> ,
> `src/LampArrayReportDescriptor.h`, MIT licensed, generated by
> [WaratahCmd.exe](https://github.com/microsoft/hidtools) from HID Usage Tables
> 1.4.

They were not written from memory and not hand-assembled. Microsoft's Dynamic
Lighting documentation points at that repository as the reference
implementation, which makes it the closest thing to a known-good encoding of a
descriptor Windows accepts. Every item was then cross-checked field by field
against HUT 1.4 section 26.

**Do not edit these bytes by hand.** To change the descriptor, regenerate it
with Waratah and update `CLA_LAMP_ARRAY_DESCRIPTOR_SIZE` and the
`CLA_PAYLOAD_SIZE_*` constants to match.

## How it is kept honest

The report sizes are derived **twice, by independent means**:

- by hand, as the `CLA_PAYLOAD_SIZE_*` constants in `LampArrayProtocol.h`,
  which the driver and service compile against;
- mechanically, by `ClaParseHidDescriptor` walking the descriptor bytes and
  accumulating `ReportSize x ReportCount` per report id.

`tests/HidTests/DescriptorTests.cpp` asserts the two agree, and separately
asserts them against the literal figures documented in the Microsoft header
(22 / 2 / 28 / 50 / 9 / 1) so that changing the constants alone cannot make the
comparison vacuously pass. `tools/DescriptorDump --check` runs the same
validation as a standalone command, and CI runs it on every push.

## Reading the descriptor

`tools/DescriptorDump` prints it fully decoded:

```
$ DescriptorDump
  off  bytes             item
  ---  ----------------  ----
    0  05 59             UsagePage(Lighting And Illumination [0x0059])
    2  09 01             Usage(LampArray [0x0001])
    4  A1 01             Collection(Application)
    6  85 01                 ReportId(1)
    8  09 02                 Usage(LampArrayAttributesReport [0x0002])
   10  A1 02                 Collection(Logical)
   ...
```

`--check` validates and exits non-zero on failure, `--bytes` emits raw hex, and
`--c-array` emits a C array for pasting into firmware.

## The six reports

All are **Feature** reports. The descriptor declares no Input and no Output
main items at all, which is why the driver registers exactly two VHF callbacks
and has no read-report path.

| Id | Report | Payload | Transfer |
|----|--------|---------|----------|
| 1 | `LampArrayAttributes` | 22 B | 23 B |
| 2 | `LampAttributesRequest` | 2 B | 3 B |
| 3 | `LampAttributesResponse` | 28 B | 29 B |
| 4 | `LampMultiUpdate` | 50 B | 51 B |
| 5 | `LampRangeUpdate` | 9 B | 10 B |
| 6 | `LampArrayControl` | 1 B | 2 B |

"Transfer" includes the leading report id byte. HIDCLASS places the report id
at `reportBuffer[0]` and counts it in `reportBufferLen` when the descriptor
uses report ids -- see `docs/research.md` for the evidence.

## Wire layouts

Byte offsets are counted from the start of the transfer buffer, so offset 0 is
the report id.

### Report 1 - LampArrayAttributes (GET)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | report id (1) |
| 1 | 2 | `LampCount` |
| 3 | 4 | `BoundingBoxWidthInMicrometers` |
| 7 | 4 | `BoundingBoxHeightInMicrometers` |
| 11 | 4 | `BoundingBoxDepthInMicrometers` |
| 15 | 4 | `LampArrayKind` |
| 19 | 4 | `MinUpdateIntervalInMicroseconds` |

### Report 2 - LampAttributesRequest (SET)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | report id (2) |
| 1 | 2 | `LampId` |

### Report 3 - LampAttributesResponse (GET)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | report id (3) |
| 1 | 2 | `LampId` |
| 3 | 4 | `PositionXInMicrometers` |
| 7 | 4 | `PositionYInMicrometers` |
| 11 | 4 | `PositionZInMicrometers` |
| 15 | 4 | `UpdateLatencyInMicroseconds` |
| 19 | 4 | `LampPurposes` |
| 23 | 1 | `RedLevelCount` |
| 24 | 1 | `GreenLevelCount` |
| 25 | 1 | `BlueLevelCount` |
| 26 | 1 | `IntensityLevelCount` |
| 27 | 1 | `IsProgrammable` |
| 28 | 1 | `InputBinding` |

Note that the descriptor declares `UpdateLatency` (usage 0x27) **before**
`LampPurposes` (usage 0x26), even though the usage ids run the other way. The
descriptor's declaration order defines the wire layout, so that is what the
code follows. This is exactly the sort of detail that would be got wrong by
writing the layout from the usage table instead of from the descriptor.

### Report 4 - LampMultiUpdate (SET)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | report id (4) |
| 1 | 1 | `LampCount` (populated slots, 0..8) |
| 2 | 1 | `LampUpdateFlags` |
| 3 | 16 | `LampIds[8]`, 2 bytes each |
| 19 | 32 | `Colors[8]`, 4 bytes each (R, G, B, Intensity) |

Eight slots, fixed by the descriptor's `ReportCount(8)`. Slots at or beyond
`LampCount` must be ignored (HUT 1.4 s26.11.1).

### Report 5 - LampRangeUpdate (SET)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | report id (5) |
| 1 | 1 | `LampUpdateFlags` |
| 2 | 2 | `LampIdStart` |
| 4 | 2 | `LampIdEnd` |
| 6 | 4 | colour (R, G, B, Intensity) |

The range is inclusive at both ends.

### Report 6 - LampArrayControl (SET)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | report id (6) |
| 1 | 1 | `AutonomousMode` (0 or 1) |

## Serialisation

The core reads and writes these layouts **field by field with explicit
little-endian helpers**, rather than overlaying a packed struct on the buffer.

That is a deliberate choice. The same code is compiled by MSVC for kernel mode
and by GCC/Clang for the tests, and casting a byte buffer to a packed struct
brings struct-packing differences, unaligned access and strict-aliasing into a
place where a mistake is silent memory corruption in kernel mode. Explicit
serialisation costs a few lines and removes the whole class of problem. The
byte offsets are fixed by the descriptor and asserted by the tests.

## One descriptor, every device

The descriptor carries no lamp count. `LampCount` is runtime data in report 1,
and every `LampId` field is 16 bits wide. A single 292-byte descriptor
therefore serves every virtual device this driver creates, up to 65535 lamps --
which is why the driver can host many LampArrays of different sizes without
generating a descriptor per device.
